# wgp2p — свой WireGuard-хаб для связи собственных машин между собой

Отдельный WireGuard-интерфейс, через который личные машины видят друг друга по
внутренним IP (ssh, любые TCP/UDP-порты, ping, rsync, syncthing, dev-серверы),
**не мешая** одновременно поднятому VPN через openconnect.

Комплект самодостаточный: каталог целиком переносится на любой сервер, см.
[Перенос на другой сервер](#перенос-на-другой-сервер).

## Зачем это нужно

VPN (openconnect/AnyConnect) режет трафик клиент-клиент: две
машины, подключённые к одному VPN, друг друга не видят. Пробросить порты
или зайти по ssh с ноутбука на десктоп через него нельзя.

Решение — собственный оверлей поверх интернета, где обе машины получают
стабильные внутренние адреса, а маршрутизацию между ними делает VPS.

## Почему именно отдельный интерфейс

**Почему не переиспользовать существующий WireGuard-инстанс (wg-easy).**
Во-первых, там могут быть чужие пиры: включение client-to-client открыло бы
машины всем клиентам того инстанса. Во-вторых, его конфиги обычно full-tunnel.

**Почему нельзя full-tunnel рядом с VPN.** `wg-quick` при
`AllowedIPs = 0.0.0.0/0` не просто ставит маршрут, а поднимает policy routing:

```
ip rule add not fwmark <mark> lookup <table>   # приоритет выше main
```

Это правило перебивает **все** маршруты из таблицы main, включая split-tunnel
маршруты, которые openconnect добавил для подсетей. Доступ отваливается
целиком.

**Что делает этот комплект вместо того.** Клиентам выдаётся
`AllowedIPs = <подсеть>/24` — единственный обычный маршрут в таблице main, без
fwmark и без `ip rule`. Он более специфичен, чем `default`, и не пересекается ни
с одной подсетью, поэтому оба туннеля живут одновременно и независимо.
Проверить это на клиенте:

```bash
ip rule                          # должны быть только local/main/default
ip route get 10.66.66.3          # -> dev wgp2p
ip route get <адрес в сети> # -> dev tun0, как и было
```

## Топология и адресация

```
   desktop-amd 10.66.66.2 ─┐
                            ├─► VPS (хаб) 10.66.66.1  ◄─ форвардит между пирами
   laptop-intel 10.66.66.3 ─┘        UDP 51830
```

| Узел         | Адрес в туннеле | Как настроен                     |
|--------------|-----------------|----------------------------------|
| VPS (хаб)    | `10.66.66.1`    | этот комплект, `wg-quick@wgp2p`  |
| desktop-amd  | `10.66.66.2`    | NixOS, `networking.wireguard`    |
| laptop-intel | `10.66.66.3`    | CachyOS, `wg-quick@wgp2p`        |

Хаб виден изнутри туннеля по `10.66.66.1`, поэтому сервисы самого VPS доступны
пирам без публикации портов в интернет.

## Почему такие параметры

Все три значения лежат в `wgp2p.env` с этими же обоснованиями.

**Порт `51830/udp`.** Стандартный `51820` уже занят другим WireGuard-инстансом.
Если провайдер VPS фильтрует нестандартные UDP-порты (симптом: хендшейка нет
вообще), достаточно поменять `WG_PORT` и переустановить — клиентам нужно
поправить только `Endpoint`.

**Подсеть `10.66.66.0/24`.** Выбрана так, чтобы не пересекаться ни с чем из уже
занятого: (`10.43/16`, `10.45/16`, `100.64.1.0/24`, `192.168.241/24`, `192.168.0.0/24`, `10.42.0.0/24`, `172.17–172.24`, `10.8.0.0/24`).
Пересечение сломало бы либо доступы, либо локальные сервисы — проверяй это
перед сменой подсети:

```bash
ip route get 10.66.66.1   # должно уходить наружу, а не в tun0
```

**MTU `1360`.** Дефолт WireGuard — 1420 (1500 − 80). Здесь ниже, потому что
клиент может оказаться в сети, где `Endpoint` попадает **внутрь** тоннеля
(другая authgroup даёт другой набор маршрутов; `tun0` MTU обычно 1422). Тогда
WG-пакет должен влезть с учётом оверхеда IP+UDP+WireGuard (60 байт):
`1422 − 60 = 1362`, берём 1360 с запасом. Цена — около 4% пропускной способности
на обычном ethernet; выгода — отсутствие чёрных дыр PMTU в чужих сетях, где ssh
подключается, а `scp` зависает на первом большом пакете.

**Без NAT.** MASQUERADE сознательно не настраивается: интернет через этот туннель
не ходит, у клиентов в `AllowedIPs` только собственная `/24`. Меньше прав — меньше
способов случайно отправить весь трафик через VPS.

**Без DNS.** В клиентских конфигах нет `DNS =`: `wg-quick` с этой директивой
перепишет `resolv.conf` и сломает DNS VPN.

## Состав каталога

```
/opt/wgp2p/
├── README.md      этот файл
├── wgp2p.env      единственный источник правды: IFACE, WG_PORT, SUBNET, ENDPOINT_HOST, MTU
├── install.sh     идемпотентная установка: пакеты, ключи, конфиг, sysctl, симлинк, автозапуск
├── add-peer.sh    добавление пира, применение через wg syncconf без разрыва соединений
├── wgp2p.conf     рабочий конфиг хаба (/etc/wireguard/wgp2p.conf — симлинк сюда)
├── keys/          server.key, server.pub      (0600)
└── peers/         <имя>.conf, <имя>.pub, <имя>.psk (0600)
```

Конфиг лежит здесь, а не в `/etc/wireguard`, чтобы всё состояние хаба было в одном
каталоге: скопировал каталог — перенёс хаб. `wg-quick@wgp2p` читает строго
`/etc/wireguard/wgp2p.conf`, поэтому `install.sh` делает туда симлинк.

## Установка с нуля

```bash
# 1. Скопировать каталог на сервер
rsync -a --exclude keys --exclude peers ./wgp2p/ root@server:/opt/wgp2p/

# 2. Поправить публичный адрес (и порт, если нужен другой)
ssh root@server 'nano /opt/wgp2p/wgp2p.env'

# 3. Установить
ssh root@server '/opt/wgp2p/install.sh'
```

`install.sh` ставит `wireguard-tools` (apt/pacman/dnf/apk), проверяет поддержку
WireGuard в ядре реальным созданием интерфейса, генерирует ключи хаба, создаёт
конфиг, включает `net.ipv4.ip_forward`, делает симлинк и поднимает
`wg-quick@wgp2p` в автозапуск. Повторный запуск безопасен: ключи не
перегенерируются, пиры не теряются, живой интерфейс обновляется через
`wg syncconf` без разрыва соединений.

## Добавление пира

Два режима — выбирай по клиенту.

**Приватный ключ остаётся на клиенте** (предпочтительно; обязательно для
декларативных клиентов):

```bash
# на клиенте:
wg genkey | sudo tee /etc/wireguard/wgp2p.key >/dev/null   # приватный, никуда не уезжает
sudo chmod 600 /etc/wireguard/wgp2p.key
sudo wg pubkey < /etc/wireguard/wgp2p.key                  # его и отдаём серверу

# на сервере:
sudo /opt/wgp2p/add-peer.sh --name my-machine --pubkey <публичный ключ>
```

**Ключи генерируются на сервере** (удобно для телефонов и одноразовых машин):

```bash
sudo /opt/wgp2p/add-peer.sh --name my-phone
# готовый конфиг: /opt/wgp2p/peers/my-phone.conf
```

Адрес выдаётся автоматически (следующий свободный) либо вручную через
`--ip 10.66.66.7`. Preshared key генерируется всегда — это дополнительный
симметричный слой поверх обычного handshake.

## Удаление пира

```bash
# 1. Убрать с живого интерфейса
sudo wg set wgp2p peer "$(cat /opt/wgp2p/peers/<имя>.pub)" remove

# 2. Убрать блок из конфига (найди "# peer: <имя>" и удали его вместе с [Peer])
sudo nano /opt/wgp2p/wgp2p.conf

# 3. Убрать файлы пира
sudo rm /opt/wgp2p/peers/<имя>.{conf,pub,psk}
```

## Настройка клиентов

### Обычный Linux (systemd)

```bash
ssh root@server 'cat /opt/wgp2p/peers/<имя>.conf' \
  | sudo install -m 600 /dev/stdin /etc/wireguard/wgp2p.conf
sudo systemctl enable --now wg-quick@wgp2p
```

Секрет идёт напрямую с сервера в файл, минуя буфер обмена и историю шелла.
Если приватный ключ генерировался на клиенте — в конфиге есть строка-заглушка
`PrivateKey = ВПИШИ_...`, замени её на содержимое своего `wgp2p.key`.

### NixOS (декларативно)

Приватный ключ и preshared key — файлами вне git, конфиг ссылается на пути:

```nix
networking.wireguard.interfaces.wgp2p = {
  ips = [ "10.66.66.2/32" ];                        # /32: маршрут даёт allowedIPs
  privateKeyFile = "/etc/nixos/secrets/wgp2p.key";
  mtu = 1360;
  peers = [{
    publicKey = "<публичный ключ хаба>";
    presharedKeyFile = "/etc/nixos/secrets/wgp2p.psk";
    allowedIPs = [ "10.66.66.0/24" ];                # только подсеть, не 0.0.0.0/0
    endpoint = "185.196.117.103:51830";
    persistentKeepalive = 25;
  }];
};
```

Забрать preshared key на машину:

```bash
ssh root@server 'cat /opt/wgp2p/peers/<имя>.psk' \
  | sudo install -m 600 /dev/stdin /etc/nixos/secrets/wgp2p.psk
```

### Windows / macOS / Android

Импортировать `peers/<имя>.conf` в официальный клиент WireGuard (для мобильных
удобно `qrencode -t ansiutf8 < peers/<имя>.conf`).

## Перенос на другой сервер

### Вариант A — сохранить ключи (клиенты почти не трогаем)

Пиры продолжают работать с теми же ключами, у клиентов меняется только `Endpoint`.

```bash
# 1. Перенести каталог целиком, вместе с keys/ и peers/
rsync -a root@old-server:/opt/wgp2p/ ./wgp2p-backup/
rsync -a ./wgp2p-backup/ root@new-server:/opt/wgp2p/

# 2. Новый публичный адрес
ssh root@new-server 'sed -i "s/^ENDPOINT_HOST=.*/ENDPOINT_HOST=<новый IP>/" /opt/wgp2p/wgp2p.env'

# 3. Поднять
ssh root@new-server '/opt/wgp2p/install.sh'

# 4. Погасить старый хаб, чтобы клиенты не цеплялись к нему
ssh root@old-server 'systemctl disable --now wg-quick@wgp2p'
```

На каждом клиенте поправить `Endpoint`:

```bash
sudo sed -i 's/^Endpoint = .*/Endpoint = <новый IP>:51830/' /etc/wireguard/wgp2p.conf
sudo systemctl restart wg-quick@wgp2p
```

На NixOS — поправить `endpoint` в модуле и пересобрать.

Файлы в `peers/` после переноса содержат старый `Endpoint` — обнови их, если
планируешь переустанавливать клиентов из них:

```bash
sed -i 's/^Endpoint = .*/Endpoint = <новый IP>:51830/' /opt/wgp2p/peers/*.conf
```

### Вариант B — с нуля

Перенести только скрипты (`--exclude keys --exclude peers`), запустить
`install.sh`, заново добавить пиров через `add-peer.sh`. Дольше, зато не тащит
старые ключи — так стоит делать, если старый сервер мог быть скомпрометирован.

## Диагностика

Проверять сверху вниз — почти всегда проблема на первом же шаге.

**Хендшейка нет вообще** (`latest handshake` пустой):

```bash
wg show wgp2p                                   # на клиенте и на сервере
sudo ss -lunp | grep 51830                      # на сервере: хаб слушает порт?
sudo tcpdump -ni any udp port 51830             # на сервере: пакеты клиента доходят?
```

Если пакеты не доходят — фильтрует провайдер или облачный firewall (правило в
конфиге открывает только локальный INPUT). Смени `WG_PORT` и переустанови.

**Хаб пингуется, а второй пир — нет:** трафик режется в FORWARD.

```bash
sudo iptables -S FORWARD | head              # policy DROP?
sudo iptables -S FORWARD | grep wgp2p        # наши ACCEPT на месте?
sysctl net.ipv4.ip_forward                   # должно быть 1
```

Правила ставит `PostUp` при старте интерфейса. Если docker-демон перезапускался
после подъёма интерфейса и перестроил цепочки — достаточно
`systemctl restart wg-quick@wgp2p`.

**ssh подключается, а `scp`/`git` зависают на больших файлах:** MTU. Понизь
`MTU` в `wgp2p.env` и в клиентских конфигах (`1280` — гарантированно рабочий
минимум) либо добавь на хабе клампинг MSS:

```bash
sudo iptables -t mangle -A FORWARD -o wgp2p -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

**VPN перестал работать после подъёма туннеля:**

```bash
ip rule                            # ничего лишнего кроме local/main/default
ip route get <адрес в сети>   # должно быть dev tun0
```

Если появился `not fwmark ... lookup ...` — у клиента в `AllowedIPs` попал
`0.0.0.0/0`. Так быть не должно, исправь на `<подсеть>/24`.

**Пир виден, но порт закрыт:** это firewall самого клиента, а не туннеля.
Проверяй `ss -ltnp` и правила на целевой машине.

## Границы решения

- **Трафик всегда идёт через VPS.** WireGuard сам не умеет NAT traversal, прямых
  соединений между пирами тут нет. Для ssh и портов задержка незаметна, для
  многогигабайтных передач в пределах одной локалки используй локальные адреса.
- **Только IPv4.** Достаточно для задачи; IPv6 усложнил бы подбор незанятой
  подсети.
- **Пиры описываются вручную.** Это осознанно: две-три статичные машины не
  оправдывают координационный сервис (Tailscale/headscale). Плюс Tailscale
  адресует из `100.64.0.0/10` и его `ip rule` перебил бы маршрут на
  `100.64.1.0/24` — ровно та проблема, от которой этот комплект уходит.
